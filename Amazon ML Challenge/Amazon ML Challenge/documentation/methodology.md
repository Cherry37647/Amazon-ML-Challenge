# Methodology

## 1. Methodology Used

The solution follows a multi-stage business entity resolution pipeline:

1. Preprocess and normalize business names and addresses.
2. Generate candidate entity pairs using blocking.
3. Generate pairwise similarity features for each candidate pair.
4. Train a LightGBM binary classification model to predict whether a pair represents the same business.
5. Select the decision threshold using validation macro F0.5.
6. Generate the final matching results.
7. Validate the final output before submission.

Only the challenge-provided data is used. No external business databases, APIs, geocoding services, or external identity lookup services are used.

---

## 2. Candidate Generation / Blocking Strategy

The final candidate set is generated using country-scoped exact lookup based on:

- Normalized business name
- Suffix-stripped business name
- Normalized business address

The candidates obtained from these lookup fields are combined, deduplicated, and sorted.

Both Source 2 and Source 3 records are considered as possible candidates for each Source 1 entity.

The final candidate pairs are stored in:

`data/candidate_pairs.tsv`

The matching model evaluates only these candidate pairs instead of performing an all-pairs comparison.

---

## 3. Model Architecture and Feature Engineering

A LightGBM binary classification model is used for entity matching.

The model predicts:

- `1` — matching entities
- `0` — non-matching entities

### Business Name Features

- Normalized name similarity
- Token-sort similarity
- Token-set similarity
- Jaro-Winkler similarity
- Levenshtein similarity
- Character/token overlap
- Exact-name indicator
- Suffix-stripped name similarity

### Address Features

- Normalized address similarity
- Token-based similarity
- Jaro-Winkler similarity
- Levenshtein similarity
- Exact-address indicator
- Address length differences

### Numeric and Other Features

- Digit overlap
- PIN/postal-code matching
- Extracted numeric information
- Country match
- String length differences

The trained model produces a matching probability for each candidate pair.

---

## 4. Threshold Selection

The challenge uses macro F0.5 as the evaluation metric.

The decision threshold is selected using validation macro F0.5 rather than assuming a fixed threshold of 0.50.

The selected threshold is stored in:

`model/threshold.json`

The same threshold is used during final prediction.

---

## 5. Final Matching

The trained model is applied only to the candidate pairs generated by the blocking stage.

Candidate pairs whose predicted probability meets the selected threshold are treated as matches.

The final output is written to:

`output/matching_results.tsv`

The output contains exactly two columns:

- `source1_entity_id`
- `matched_entity_ids`

Every Source 1 test entity receives exactly one row. If no match is predicted, the `matched_entity_ids` field is left empty.

Predicted matched IDs are restricted to valid Source 2 or Source 3 IDs present in the test data and in the candidate set.

---

## 6. Validation and Compliance

Before submission, the final output is checked for:

- Exactly one row for every Source 1 test entity
- Duplicate Source 1 IDs
- Duplicate matched entity IDs
- Invalid Source 2 or Source 3 IDs
- Invalid Source 1 self-matches
- Matches that are not present in the candidate set
- Correct TSV format
- Correct handling of entities with no predicted match

The official challenge validator is run on the final output before packaging.

The pipeline treats country as a general string attribute and does not hardcode the training countries, allowing unseen country labels in the test data to be processed.
